## 一、酒吧点单接轨（出酒 → 前台接单）

### 1.1 一句话
玩家在调酒页摇出的那杯虚拟酒，一键变成吧台上的真酒：**映射规则是商家可自助配置的 JSON**，出酒页出现「把这杯变成真的」入口，前台在接单端看到订单和取酒码，叫号交付。

### 1.2 用户流程（玩家侧 / 前台侧）

```
玩家侧：出酒页 →「在本店喝到这杯 ¥48」CTA
       → 确认单（真实酒名/价格/桌号或取酒码）→ 支付（MVP：到吧台付，报取酒码）
       → 等叫号 → 取酒（老K文案：「去吧台，报这串号，别报我名字。」）

前台侧：接单端（平板/手机开 /staff/:venueId，无需装 App）
       → 新订单响铃：#A17 ·「旧码头·酸甜审判」→ 映射为「金汤力 ¥48」· 3号桌
       → 点「开始做」→「叫号」→ 玩家核销取酒码 → 完成
```

要点：
- **虚拟酒名保留在订单上**（「旧码头·酸甜审判 → 金汤力」），交付时的仪式感是传播点，杯垫/小票可打印虚拟酒名。
- 线上局（玩家不在店内）：CTA 降级为「收藏这杯，到店兑换」，生成 7 天有效兑换码——即拉新到店的钩子。
- 支付 MVP 不做在线收款（免牌照/对账负担），吧台线下收款 + 前台端手动标记已付；在线支付留到二期（见 1.5 商务留口）。

### 1.3 映射配置 JSON（商家可自助换菜单/价格）

映射输入是调酒结果的确定性向量 `answers = [base, mixer, garnish, ice]`（各 0..3，见 `public/v2/cocktail.js` 的 `resolveCocktail`）。分四层命中，从精确到兜底：

```jsonc
// venue-config/{venueId}.json —— 商家侧唯一需要维护的文件
{
  "venueId": "bar-huoshan-001",
  "venueName": "火山口酒吧",
  "currency": "CNY",
  "updatedAt": "2026-07-29T20:00:00+08:00",
  "menu": [
    { "sku": "gt-01", "name": "金汤力", "price": 48, "abv": "中", "img": "https://…", "soldOut": false },
    { "sku": "mg-01", "name": "玛格丽特", "price": 58, "abv": "中高", "img": "https://…", "soldOut": false },
    { "sku": "nb-01", "name": "无酒精特调·假装喝醉", "price": 38, "abv": "0", "img": "https://…", "soldOut": false }
  ],
  "mapping": {
    "overrides": [                        // 第1层：精确组合（可空）——商家想给某杯"命定款"时用
      { "when": { "base": 0, "mixer": 2, "garnish": 1, "ice": 3 }, "sku": "mg-01" }
    ],
    "byBaseMixer": { "0-2": "mg-01" },    // 第2层：基酒×辅料（16 键，覆盖主要口感分区）
    "byBase": { "0": "gt-01", "1": "gt-01", "2": "mg-01", "3": "mg-01" }, // 第3层：只按基酒（4 键，最低配置成本）
    "fallbackSku": "gt-01"                // 第4层：兜底，必填
  },
  "noAlcoholSku": "nb-01",               // 玩家勾选"不喝酒"时的替换（未成年/开车场景，必填）
  "service": { "mode": "counter", "tableCount": 6, "webhook": null },
  "commerce": { "commissionRate": 0.0, "sponsoredSkus": [], "redeemTtlDays": 7 }
}
```

设计原则：
- **商家最少只需要填 4 个基酒键 + 1 个兜底**就能上线（第3、4层）；精细化是可选升级，不是门槛。基酒选项扩充（FEEDBACK #4，金酒/伏特加/朗姆/威士忌/龙舌兰/白兰地…）后 `base` 维度相应扩位，映射键随之增加但结构不变。
- 配置文件校验器随仓库提供（`qa/venue-config-lint.mjs`，待建）：sku 引用必须存在于 menu、fallbackSku/noAlcoholSku 必填、价格>0。商家改错不上线。
- 存储：KV `VENUES:{venueId}`；MVP 由我们代维护 JSON，商家发菜单照片/Excel 我们录入——**自助后台是二期**，先跑通「一家店」。

### 1.4 订单数据结构与接口

```jsonc
// Order（DO: VenueDO 内存 + storage 持久化）
{
  "orderId": "od_9x2k",
  "venueId": "bar-huoshan-001",
  "pickupCode": "A17",              // 叫号用，日内自增
  "source": { "roomCode": "4821", "userId": "u_…", "table": 3 },   // 可空（solo/线上局）
  "cocktail": { "name": "旧码头·酸甜审判", "answers": [0,2,1,3], "paletteId": 2 },
  "sku": "gt-01", "skuName": "金汤力", "price": 48,
  "status": "created",              // created → claimed(开始做) → served(已交付) / cancelled / expired
  "paid": false,
  "createdAt": 1753790000000,
  "redeemBy": null                  // 线上局兑换码模式才有：过期时间
}
```

接口（沿用 Worker + DO 架构，新增 VenueDO 一类实例，`idFromName(venueId)` 天然串行防并发）：
- `GET  /api/venue/:id/config` — 玩家侧拉映射+菜单（只读，缓存 5 分钟）
- `POST /api/venue/:id/order` — 出酒页下单，返回 `{orderId, pickupCode}`
- `GET  /api/venue/:id/orders?status=…` — 前台端轮询（MVP）或 WS 推送（复用 DO WebSocket 能力）
- `POST /api/venue/:id/order/:oid/status` — 前台端流转状态（需 staffKey，配置在 venue JSON 外的 secret）
- `webhook`（可选）：订单创建时 POST 到商家配置的 URL（飞书群机器人/打印机盒子），店里没人盯平板也能接单

### 1.5 商务留口（本期不做，字段先留）
1. **抽成**：`commerce.commissionRate` 已进 schema；在线支付接入后按单结算，线下收款期为 0。
2. **品牌位**：`sponsoredSkus` —— 酒厂联名款可被映射层优先命中（如「本月伏特加基酒统一出 XX 联名款」），按位收费。
3. **数据报表**：订单表天然沉淀「玩了什么局→点了什么酒」的转化漏斗，日报（杯数/客单/兑换率）是对商家的续费抓手。
4. **多门店**：venueId 即租户；桌子二维码（海报二维码已跳 `/?room=CODE`，FEEDBACK #19）加 `&venue=ID` 参数即完成店内归因。
5. **核销激励**：图鉴全收集送免单券（见第二节 2.4），券也走 Order 流，`price:0` + `note:"图鉴奖励"`。

## 二、图鉴系统（原型有限集合 + 集齐 + 撞型裂变）

### 2.1 前提：与「AI 只写相处细节」的关系（采纳 0729 PM 决策）
双层结构，各司其职：
- **原型层 = 有限集合，确定性生成，可图鉴化**。撞型（"我也是这型"）是裂变入口，必须可枚举、可编号、可统计稀有度。绝不让 LLM 参与原型判定，否则集合失控、图鉴失效。
- **细节层 = LLM 自由发挥，保证同型不同人**。调酒问卷 + 本局打分记录交叉进相处细节 prompt，两个同为 #07 原型的人，相处细节完全不同——收藏的是「型」，留住人的是「细节」。
- 现状差距：`ideal-profile.js` 的 archetype 是 形容词(8维×3档) × 名词(8维×3档) 自由拼装，组合空间 576，**不可图鉴**。需要收敛（下节）。

### 2.2 每模组固定几个原型：16 vs 25，选 16

| 维度 | 16（4×4） | 25（5×5） |
|---|---|---|
| 算法映射 | **自然**：top1 维度捆绑为 4 大族（心界/火热/掌舵/野生）× top2 档位 4 型，确定性落桶 | 需要 5 分法，与现有 8 维×3 档结构都不整除，映射发硬 |
| 集齐成本 | 优惠券收集问题期望 ≈ 16×H₁₆ ≈ **54 局**——重度玩家一两个月可达成，普通玩家集齐一排(4个)也有正反馈 | ≈ 25×H₂₅ ≈ **95 局**，超出酒桌局复购现实，图鉴变永久烂尾工程 |
| 撞型率 | 单模组内撞型概率高 → 「我也是这型」更容易发生，**裂变靠撞** | 撞型率低，稀有感强但社群难起量 |
| UI | 4×4 一屏放下（390 宽），海报角标「#07/16」干净 | 5×5 手机端格子过小 |
| 总量 | 5 模组 × 16 = **80 个原型**，美术（像素立绘）工作量可控 | 5 × 25 = 125 个，美术翻 1.5 倍 |

**结论：16。** 25 留作「第二季」扩容位——图鉴 UI 预留「？？？」隐藏行，等 DAU 证明复购再加。

### 2.3 原型判定（确定性，替换现有自由拼装）
- 8 维打分向量（现有 `computeDimensions` 不动）→ top1 维度归入 4 大族（边界+掌控=秩序族；情绪+浪漫=火热族；玩心+抽象=野生族；金钱+网感=世俗族）→ × top2 维度在族内的 4 种落位 = **16 桶**。
- 每桶固定：编号（#01–#16）、名称（从现有 ADJ×NOUN 里精选 16 个定死，如「#07 边界感精装修的人形保险柜」）、像素立绘（固定 seed，不再随机）、一句老K评语。
- 5 个模组共用 16 桶算法、各自换皮（agent 模组的 #07 叫「护主型防火墙」之类），文案表驱动。
- 同分向量永远落同桶：可复现、可申诉、可统计——这是稀有度公示的前提。

### 2.4 集齐机制
- **入账**：每局 aha 生成即写入（伴随 FEEDBACK #15 的展示柜直存），`user.codex[module][archetypeId] = { count, firstAt, seeds[] }`。重复抽到 = count+1，显示「×3」，不是废卡——count 进稀有度榜。
- **图鉴页**：展示柜加「图鉴」tab（F 线程今晚占位）。未解锁 = 剪影 + 编号；已解锁 = 像素立绘 + 首次获得日期 + 该型全网占比（周更）。
- **阶梯奖励**：集齐一排(4) → 解锁该族隐藏称号 + 老K一句限定语；集齐一个模组(16) → 解锁隐藏锅底一副；全图鉴(80) → 实体奖励，接第一节：合作酒吧免单券（`price:0` 订单）。
- **防刷**：同房间同晚重复局只计首局入账；solo 局可入账但不进稀有度统计。

### 2.5 撞型社群裂变
1. **海报即撞型广告**：海报（已带房间二维码）加原型角标「#07 人形保险柜 · 全网 3.2%」。扫码进的不只是房间，是「和 TA 同型的人开的房间」。
2. **撞型时刻**：同桌两人 aha 出同一原型 → 全屏彩蛋（老K：「今晚这桌，有两个一样的灵魂。这杯我请。」）——可截图，天然传播物料。
3. **同型频道**：MVP 不自建社区，图鉴详情页给「同型暗号」（如 `#07-保险柜`）引导用户自发在群昵称/小红书 tag 使用；二期再做站内同型房间快捷入口（大厅公开桌按原型筛选，接 FEEDBACK #10 公开桌能力）。
4. **稀有度周报**：每周公示 16 型分布（KV 聚合计数即可），「本周最稀有：#13 赛博纯真的词典派学者，全网 0.8%」——稀有型玩家有晒的理由，常见型玩家有找组织的理由，两头都是内容。

### 2.6 落地顺序建议
1. 先收敛原型到 16 桶（算法半天，文案表 1 天，立绘 seed 固定化半天）——**这是图鉴、稀有度、撞型的共同地基**；
2. 图鉴 tab 读 user.codex 渲染（1 天）；
3. 海报角标 + 撞型彩蛋（半天）；
4. 稀有度周报与阶梯奖励随运营节奏开。
