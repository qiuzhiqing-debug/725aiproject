## 4. 核心机制设计（Phase 3，先捋清，分批实现）

### 4.1 生图×标签×分布 → 固定 TYPE（#7 #4）
- 现状：`buildIdealProfile` 由 8 维分布**算法拼**出 archetype/occupation/bio/立绘 prompt——已经是"分布→人物"，但**每次都是连续生成、无固定类型**，无法"收集"。
- R7：每款定义一组**固定理想型 TYPE**（如满分男：文艺暖男/钝感硬汉/双门电竞少年/自律清冷学长…每款 8–12 个 + 3 隐藏款）。8 维分布 → **映射到最接近的 TYPE**（top1/top2 维度档位 → TYPE 查表），TYPE 决定：剪影图、人设底、立绘 prompt 主体。→ 用户答题结果稳定落到某个可收集 TYPE，图鉴才有"集齐"的意义。

### 4.2 人设内部档（#8）
- 每个 TYPE 写一份**完整人设**（性格/背景/说话方式/雷点/名场面），存**内部档**（如 `public/personas/<module>.js` 或 ideal-profile 扩展），**不全给用户**——只把"总结好的标签"放封面(#9)。
- 用途：驱动立绘 prompt、档案卡口吻一致、相处细节选取，未来可做"人设一致的对话/续写"。

### 4.3 封面→档案卡 两张图（#9）
- **第一张=封面/立绘**：TYPE 剪影/立绘 + **总结标签**（现有 keywords 逻辑复用）。
- **点击→第二张=档案卡**：沿用现有 `matchCard`（相亲档案页）逻辑，字段在 TYPE 范畴内随机组合。

### 4.4 抽卡（#11）
- 一个 TYPE（一张人设图/剪影）对应 **X 张档案卡**：职业/MBTI/出生/小传/相处细节从"属于该 TYPE 范畴"的池随机组合 → 用户每次抽到同 TYPE 但细节不同的一张卡，收集感 + 复玩性。

### 4.5 相处细节 = 人格 × 模组 交叉（#12，Deploy1 起步）
- Deploy1：`DETAIL_POOL` 按 `m:`（模组）+ `d:`（维度）+ `t:`（档位 high/low）三维索引，`pickDetails` 按"当前模组 × top 维度档位"抽取，**非 lover 模组 0 条恋爱味**（profiler 线程执行中）。
- Phase3：把每模组细节池扩到"足够多、随机不重复"（每模组每维 high/low 各 ≥3 条）。
